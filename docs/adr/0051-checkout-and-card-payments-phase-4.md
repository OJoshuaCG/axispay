# ADR-0051: Checkout and card payments (Phase 4), built without Stripe keys behind an acceptance gate

- **Status:** Accepted (owner decisions of 2026-09-27). **Phase 4 acceptance is conditional** on the Stripe acceptance gate below.
- **Date:** 2026-09-27
- **Source:** master plan sections 6.3, 7.5, 9, 11, 12, 14, 19, 23, 26.2 (cases 1, 2, 3, 4, 16, 17, 20) and 27 (Phase 4); [ADR-005](0005-own-domain-payment-element.md), [ADR-006](0006-single-use-reopenable-links.md), [ADR-017](0017-own-db-source-of-truth.md), [ADR-018](0018-card-only-mvp.md), [ADR-019](0019-gateway-port-adapter.md), [ADR-0038](0038-platform-branding-powered-by.md), [ADR-0047](0047-stripe-connection-phase-2-and-api-key-reordering.md), [ADR-0049](0049-panel-money-formatting-and-tenant-timezone.md), [ADR-0050](0050-linear-payment-flow-authorize-validate-capture.md); the approved checkout design spec (DESIGN.md of the Phase 4 job).

## Context

Phase 4 delivers the public payment page, payment attempts, 3D Secure, the completion page, the handling of Stripe's payment events, reconciliation, card-testing protection, security headers and the recording of openings. The plan asks for a technical spike with Stripe test mode first. The platform does not have Stripe test keys yet, and the owner does not want to wait for them.

## Owner decisions (2026-09-27)

1. **Build without Stripe keys.** The Stripe adapter is written from Stripe's current documentation (sources below) and exercised with Stripe's HTTP layer faked. The plan's spike becomes an **acceptance gate**: the contract tests of the `stripe` group, skipped without keys, must pass with real test-mode keys before Phase 4 is accepted.
2. **Checkout sandbox for local development and tests only**: a fake gateway on the server and a stand-in for Stripe.js in the browser, so the whole payment page can be used and tested end to end without keys. It can never run in production.
3. **Payer-facing Spanish uses "tú".** The panels keep "usted".
4. **The checkout's Content-Security-Policy includes Stripe's `*.js.stripe.com` origins**, as Stripe's CSP guide asks.

## Decision

### 1. The payment page

- `https://<pay host>/l/{token}`: the page. `/l/{token}/attempts` (pay), `/l/{token}/attempts/continue` (after 3D Secure; an addition to plan 11.5), `/l/{token}/status` (polled) and `/l/{token}/complete` (where the payer lands after paying).
- **Session and CSRF:** plan 11.5's option. The pay host has its own anonymous session with its own cookie (never shared with the panels, `SameSite=Lax`), which gives the CSRF token of the POST endpoints and remembers two things per link: the payer's own declines (for Turnstile) and whether the payer paid in this session. No payer data is kept in it.
- **Tenant resolution:** the public token is looked up by `PaymentLinkLookup` (the only cross-tenant reader of links); the tenant context of that link is then set for the rest of the request. An invalid token (malformed, unknown, another case) always runs the same query and answers the same 404 page, without merchant information.
- **Language:** the link's language, unless the payer chose one with the language switcher.
- **Closed tenants** (plan 21.3): a closed tenant's links stop taking payments at once (the page shows "no longer available" and the pay endpoint refuses), and closing the tenant cancels its active links in both modes with reason `tenant_closed` (queued, retried, idempotent; a link with a payment under way is left to finish and handled on a later run). A suspended tenant keeps collecting (ADR-013).
- **States** (plan 11.2): active, processing (polls every 3 seconds for 2 minutes, then "check again later"), paid (only the session that paid sees "Payment complete" with the amount; anyone else sees "This payment has already been made"), expired, canceled, and "not accepting payments" (long card-testing block or no gateway that can charge). An active link past its expiry is expired when the page opens. The informative states answer HTTP 200 and show the description and date, never the amount; the amount appears only while the link can be paid, during a payment and to the session that paid.
- **Status polled by the page:** the link's page state, the phase while processing and, once paid, the link's return URL. Polling never starts or refreshes a session: it is a read with no cookie. While a payment is under way the status re-reads it from Stripe when it has not changed for a while, less often the longer it stays idle (every 5 seconds, then every 10 seconds after a minute, then every 20 seconds after two minutes; configurable), so a 3D Secure step left open does not keep asking Stripe.
- **Page load:** the tenant and the tenant's connection are read once per request, whatever the page needs from them. Stripe.js loads without blocking the page and still runs before the page's own script; the page opens the connection to Stripe's API early. The card form receives only the two font weights it uses. If anything fails while paying (network, Stripe.js, an unexpected answer), the Pay button never stays busy: the payer sees the generic error and may try again.
- **Stripe.js initialization** comes from `CheckoutClientConfig`: the platform's publishable key and the connected account for `platform_onboarding` and `oauth`; the merchant's own publishable key and no account for `api_key` (plan 12.4.1, case 20). No secret key ever reaches the page.
- **Design:** implemented as the approved design spec: layout per breakpoint, no theme toggle (the page follows the operating system), copy of every state in both languages, Stripe Appearance read from the page's own colors, focus management, one polite live region, no layout shift while the card form loads.

### 2. Payment attempts

- One attempt per gateway payment (plan 7.5, 9.2). A decline does not create a new attempt: the same payment is confirmed again with another card, and every decline is recorded once in `payment_attempt_failures`.
- **At most one active attempt per link**, enforced by a unique index on a generated column (rules.md rule 9). Active means waiting for a card, waiting for confirmation, bank verification, **authorized and waiting for capture** (the stage added by ADR-0050) or processing.
- The attempt keeps the connection and the account it was created with; every later call uses them.
- A short **lease** on the attempt serializes everything that talks to Stripe about it (the payer's confirmation, a second tab, a webhook, the status sync, a void): a second tab is told a payment is in progress instead of confirming the same payment again. Each lease has an owner token; only its holder releases it, and a crashed holder's lease expires after 90 seconds.
- **The lease always outlives a gateway call.** Every Stripe call is bounded: 20 seconds per request (5 to connect), one automatic retry with the same idempotency key, at most 2 seconds between them, so at most 42 seconds, below the 90-second lease. The lease is renewed right before each call; if it was lost meanwhile (the holder was too slow and another actor took over), the slow actor stops without calling Stripe. The merchant's decision is re-read after it is stored, so the first decision stored is the one every actor applies.
- **A reservation left by a confirmation that died** (lease expired, nothing under way at Stripe) does not wait for the reconciliation: the page offers the form again and the next payment takes it over.
- **No shared gap locks.** Claiming reads the link's active attempt without a locking range read (the link's own lock already serializes that link) and then locks it by its key, so first payments of different links of one tenant never deadlock; a deadlock that still happens is retried three times and otherwise answered "payment in progress", never an error page.
- **The link is reserved while a payment is confirmed.** Claiming the attempt moves the link to `processing` in the same locked transaction. Expiry skips it and cancellation answers "payment in progress" (plan 9.1). When the confirmation ends without a payment under way (decline, error, refusal) the link becomes payable again, or expired if its expiry passed meanwhile, and the attempt's waiting payment is then canceled. A payment under way keeps the link reserved until its outcome.
- **Stale reads are not applied.** Stripe never moves an authorized payment back to "waiting for the bank or a card" on its own, so such a report is only accepted from the lease holder answering its own call; from any other read (a late event, a slow status sync) it is ignored.
- **A retried confirmation never charges twice.** If Stripe answers that the payment was already confirmed (a retry after a lost answer), the adapter returns the payment as it is now and the flow continues from there (usually to capture, once). Creation always uses the amount stored on the attempt, so a retry after a lost answer repeats the same request even if the amount to charge changed; the new amount then goes through the update. A payment waiting for the bank or processing may go back to "waiting for a card" only with a decline not recorded yet (or from the lease holder); an older read without one is ignored.
- Transitions go only through the attempt and link state machines, inside a transaction with row locks, always locking the link before the attempt. Attempts follow the gateway's current state, so any active status may follow any other (missed or out-of-order events); final statuses never change.
- Link transitions driven by attempts: a payment under way makes the link `processing`; a decline or a closed attempt makes it `active` again, or `expired` if its expiry passed meanwhile; a success makes it `paid`. **A success on an expired or canceled link wins** (ADR-006): the attempt is flagged `late_payment` (kept for the Phase 5 webhook), the anomaly is audited and logged.
- When a link expires or is canceled, its attempt still waiting for a card is closed and its Stripe payment canceled (queued, with retries). If Stripe says the payment had already succeeded, the payment wins.

### 3. The flow (ADR-0050)

1. The link must be payable (active, not past its expiry, not blocked).
2. Payer fields are validated against the configuration frozen on the link (plan 19.1).
3. Card-testing protection (section 5 below), with Turnstile verified on the server before Stripe is called.
4. The card behind the confirmation token is read (country, brand, last four digits).
5. The amount to charge is decided by one place that Phase 6 extends with currency conversion; in Phase 4 it is always the link's amount.
6. Under the link's lock the link's single attempt is reused or created, its lease taken and the payer's data stored encrypted.
7. Outside any lock: the Stripe payment is created (card only, **manual capture**, description, our identifiers only in its metadata, no application fee), then confirmed with the confirmation token. Idempotency keys are stable per attempt and operation, so a retry never creates or confirms twice.
   - **Creation carries only what the link fixes** (amount, currency, description, our identifiers), under a key fixed per attempt: after a lost answer the retry repeats the very same request and Stripe replays it. Anything that depends on the payer (the receipt e-mail) travels with the confirmation, whose key includes the confirmation token, so a payer who changes a field never meets a refused key.
   - Searching Stripe for an intent created before a lost answer is not used: the search API is eventually consistent and not guaranteed for every account, and the fixed-parameter key already makes the retry return the same intent (within Stripe's 24-hour key lifetime; an intent orphaned after that was never confirmed and cannot charge).
   - A different amount on a reused attempt (Phase 6 conversion) is an update of the same intent, with a key that names the new amount.
8. 3D Secure: the page receives the payment's client secret (never stored or logged; client secrets are masked in logs and error reports, including inside return URLs) and lets Stripe.js run the bank's verification, then calls `continue`. Only the session that was handed that step may continue that attempt, once; any other session is told a payment is in progress (it never sees a merchant message nor becomes "the session that paid"), and repeated calls are debounced per attempt.
9. **Authorized:** within the capture window (15 minutes from authorization, configurable; ADR-0050) the pre-payment validation extension point is asked, with no lock and no open transaction (rules.md rule 7b); Phase 4's default answers "not configured". **The merchant's decision is kept on the attempt at once**, so a retry, a webhook or the reconciliation never asks again and never captures a rejected authorization. The link and then the attempt are locked and re-checked: if the link was closed meanwhile (or its tenant closed) the authorization is voided instead of captured, unless Stripe says the payment already succeeded, in which case the payment wins. Approved → captured; rejected (or `fail_closed` in Phase 5) → **the authorization is voided**, nothing is charged, and the payer sees the merchant's message and the "you were not charged" notice. The void path is complete and tested so Phase 5 only plugs the callback in.
   - If the capture or the void cannot be done right now (Stripe unreachable, refused), the payer sees "your payment is processing", never an error page; the webhook or the reconciliation completes it with the kept decision.
   - **Past the capture window** the authorization is voided by whoever sees it, without asking the merchant, even if an approval was kept; a payment Stripe already reports as succeeded wins. A late event for a payer who left long ago never charges them.
   - The capture window must stay well below the card hold Stripe keeps (7 days for most cards): an authorization is never left to expire on its own.
10. The database follows what Stripe reports; Stripe's events remain the source of truth (ADR-017, ADR-0050).

**Stripe's stored answers.** Stripe stores the answer of every request that started executing under its idempotency key, server errors included, for at least 24 hours: repeating a creation, capture or void under the same key after a server error can never succeed. After a server error the payment is read again; if it moved on (captured or voided elsewhere) that state is applied, otherwise the call is repeated under a derived key, at most twice, and logged. Stripe's own rules (a payment is captured or voided once) keep a repetition from acting twice; a creation repeated this way can leave an unconfirmed intent behind, which cannot charge. The confirmation key covers every parameter that can change between two tries (the card token, the receipt e-mail and the return URL), so a payer whose receipt setting changed is never refused. A capture that finds the payment no longer capturable (captured by another process, canceled, expired) applies what Stripe reports instead of failing.

**Card only.** The payment accepts only cards (`allowed_payment_method_types`, which replaces `payment_method_types` from API version 2026-07-29.dahlia; later versions remove the old parameter), and the payment form hides wallets and Link.

**Creation and confirmation are always two separate Stripe requests** (verified across the checkout, the Stripe adapter and its contract tests, and the sandbox): the intent is created unconfirmed, then confirmed with the payer's token under its own key. A lost answer to the creation therefore never charged anyone, and an intent orphaned after Stripe's 24-hour key lifetime was never confirmed and cannot charge; a new request after that creates a new intent, and the old one stays unconfirmed. No double charge is possible from a key expiring.

Declines are always shown to the payer with one generic message; the decline code and Stripe's explanation stay in the tenant panel (plan 11.7 rule 7).

### 4. Stripe's payment events

- Handled: `payment_intent.amount_capturable_updated`, `.succeeded`, `.payment_failed`, `.processing`, `.requires_action`, `.canceled`. All are one kind for the pipeline: the handler re-reads the payment from Stripe and applies its current state (plan 14.2), which makes duplicates (case 3) and out-of-order events (case 4) harmless.
- An authorization reported by an event is completed (validation, capture): the payer who closed the tab after 3D Secure still pays once. If another process holds the attempt, one more try is queued a minute later.
- **Stored events carry no payer data.** Payment events are stored with the reduced envelope only (event, type, account, mode, the payment's ID), since the handler re-reads the payment anyway (rules.md rule 6); only account events keep their full body. **Every stored event body is encrypted at rest**, and whether it was reduced is kept as a flag, so the retention purge never reads bodies to find its work.
- **Foreign payments** (no attempt ID in the metadata, or one the tenant does not have), frequent on `api_key` and `oauth` accounts, are stored as `ignored` with reason `foreign_object` and the reduced payload, decided from the payload before any call to Stripe (plan 14.4).
- **One job per event.** While an event's job is queued, running or waiting for its next try (up to about 25 minutes over its five tries), no second job is queued for it: a duplicate delivery from Stripe, the sweeper or an operator retry leaves it alone, so an event is never processed twice at once and the sweeper does not record a retry for a job that is only waiting. Sweeping reads only what it needs to route an event (never the stored body until an event is actually routed) and looks each merchant account's connection up once per run.
- **Recovery of events.** An event is stored before its job is queued; if queuing fails after the event was stored, it would stay `received` for good. So a delivery of an event that is still `received` five minutes later (configurable) queues it again, and `axispay:provider-events:sweep` (every five minutes) queues again every event in that state. An event whose account had no connection is kept as `unroutable`; when the same event arrives again through a route that knows its connection, or the sweeper finds that the connection now exists, the routed copy replaces it and is processed. A failed event raises an alert-level log line and an audit entry (the superadmin e-mail arrives in Phase 9); the operator retries it with `axispay:provider-events:retry` (one event, by our ID or Stripe's, or every failed event with `--failed`). Every retry is audited and idempotent: an event already processed is left alone, and processing applies an event once.
- **Errors that a retry cannot fix fail at once.** Stripe refusing the credentials, or answering a request error (4xx), fails the event (or the payment job) with the reason, instead of retrying it five times. Refused credentials on any payment call of an `api_key` connection mark the connection `invalid_credentials` (only if its keys did not change meanwhile, plan 12.6) and notify the tenant; for Connect connections they are logged for review.
- **Routing.** A payment event goes to the connection that created its attempt (named in the payment's metadata), when that connection matches the event's account and mode, whatever its status now. Other events go to the account's live connection or, if there is none, to its most recent one only when every connection that account ever had belongs to the same tenant: an event is never handed to another tenant's old connection.
- **One account, one method.** An account the platform reaches through Connect keeps sending its events to the Connect destination, even after its Connect connection is disconnected. Connecting that same account with API keys is refused, so the same event never arrives through two routes. Connect onboarding always creates a new account, so the reverse cannot happen in Phase 4 (OAuth, which links existing accounts, must apply the same rule).
- **Adopting a payment by its metadata** (a crash right after creating the intent, before its ID was stored) also requires that Stripe created it while this attempt's own creation could have: from a minute before the attempt existed until its keys expire (24 hours). Residual risk: someone with access to the merchant's Stripe account could create a payment for the same amount, with our attempt ID in its metadata, inside that window; it would be adopted. That requires the merchant's own account access, and amounts must still match exactly.
- **Refunds and disputes are not subscribed in Phase 4.** Stripe does not resend events from before a subscription, so refunds and disputes made in the Stripe Dashboard between the Phase 4 go-live and Phase 7 will never arrive as events. Phase 7 must backfill them from Stripe's list endpoints (refunds and disputes per connection) from the Phase 4 go-live date before relying on events.
- Configuration: the Connect destinations of both modes and the endpoints on merchant accounts subscribe to these six events. After deploying Phase 4, run `axispay:stripe-sync-webhook-endpoints` so existing `api_key` endpoints receive them, and add the events to both Connect destinations in the Stripe Dashboard.

### 5. Card-testing protection (plan 11.7)

| Rule | Value |
|---|---|
| Per link | 5 confirmations in 15 minutes, then 30 minutes paused |
| Per client IP | 10 confirmations per hour, across links |
| Turnstile | Required once the link, or the payer's session, has 1 decline (critical case 16: "Turnstile after a decline"; the design spec's "after the 2nd failure" is read as "from the 2nd attempt, the first after a failure"). Configurable |
| Long block | 10 declines on a link in 24 hours block it for 24 hours; declines before the tenant last lifted a block do not count |
| Notification | E-mail to the tenant's owners and every user holding `links:cancel` |
| Unblock | Tenant panel, link detail, permission **`links:cancel`** (the permission that decides whether a link keeps taking payments), audited |
| Unrecognized tokens | Also 20 per client network per hour, across links |
| Superadmin alerts | Phase 9; until then an alert-level log line |

- **Counting is atomic and only counts real confirmations.** A confirmation is counted at the moment it is about to reach Stripe's confirm call, and the count is compared after it is taken: a burst of simultaneous requests can never overshoot the limit, and the one over it is taken back. Requests answered "a payment is in progress" never reached Stripe and never count, so several tabs or a double click cannot pause a link that has had no decline.
- **Bogus tokens and Stripe failures.** Tokens Stripe does not recognize also count per client network across all links (20 per hour), so rotating links does not let a client hammer Stripe. A token Stripe could not read because it was unavailable or rate limiting counts like a bogus one for that link and client.
- **Request limits of the pay host.** Each group of pages has its own budget per client and link: the payment page and the completion page 60 per minute each, the status polling of the completion page 90 per minute (it polls every 3 seconds for 2 minutes), Pay and the 3D Secure continuation 30 per minute each. Polling or reloading never eats into the budget of paying. Over a limit the payer sees "too many requests, try again in N seconds" (the page re-enables the button after that time) or a short page on reload.
- **Turnstile keys are required in production.** Without them every link would stop taking payments after its first decline, so the application refuses to start without both keys and `axispay:doctor` reports an error. If the page ever needs Turnstile without a site key (a misconfigured non-production), it says payments are unavailable instead of skipping the check, and the server logs an error.
- **A verified Turnstile token is spent.** Cloudflare accepts a token once and for 5 minutes, so after a token was verified, whatever the outcome of that payment try, the page is asked for a new one. An expired or reused token is logged apart from other refusals.
- **Card fingerprint.** Stripe's card fingerprint (the same card gives the same value on one account) is kept on attempts and declines for card-testing forensics. It is never shown to payers; the tenant panel shows only the last four digits.
- **Lifting a block is a sensitive action** and needs a recent re-authentication (password or 2FA code), like revoking an API key.
- **Accepted limits.** Superadmin alerts for card testing arrive with Phase 9 (alert-level log lines until then). A stranger who knows a link can still pause it for everyone by reaching real confirmations with real cards; that griefing is inherent to any per-link limit and the tenant can lift a long block from the panel.
- **Only real attempts count.** The limits are checked before anything else, but a confirmation only counts once Stripe recognized its confirmation token; tokens Stripe does not recognize count per link **and** client, so a stranger posting bogus tokens can only pause themselves, never the link for the real payer.
- **Client network:** the per-IP limit uses the address for IPv4 and the /64 network for IPv6 (a subscriber holds a whole /64, so rotating addresses inside it does not escape the limit).
- **Real client IPs require the proxy to be trusted.** Behind Traefik, without `TRUSTED_PROXIES` every payer would share the proxy's IP and the per-IP limit would pause payments platform-wide. In production the application refuses to boot without it, and `axispay:doctor` reports an error when it is empty or `*`.

Turnstile tokens are checked with Cloudflare's siteverify endpoint (secret, token, payer IP) before Stripe is called; any failure refuses (fail closed). Besides success, the answer must name the pay host and the `checkout` action set by the page's widget (Cloudflare's recommendation), so a token solved elsewhere is refused. Cloudflare's test keys answer with a dummy host and are accepted outside production only. The widget appears only when required, between the card form and the Pay button, always visible, compact on narrow screens. Cloudflare's documented test keys work in local and testing.

### 6. Openings (plan 11.6)

Every page view of an active link counts (`open_count`, first and last opening), except link previewers recognized by user agent (configurable list; an empty user agent counts as a previewer). `payment_link.opened` is recorded on the first opening and then at most once every 30 minutes, with the count and whether it was the first.

### 7. Business events recorded for Phase 5

`payment_link.opened`, `payment.processing`, `payment.failed` (per decline, with the count), `payment.succeeded` and `payment_link.paid` (with `late_payment`) are recorded in `domain_events` in the same transaction as the change, with our identifiers only. Phase 5 turns them into the outgoing webhook outbox; nothing is delivered in Phase 4.

The kind of a failed payment try (card declined, insufficient funds, expired card, incorrect card details, authentication failed, processing error) is decided by the gateway adapter from the gateway's own codes and kept on the attempt and the decline; the rest of the platform decides with the kind and never reads gateway codes. The raw codes are kept only for the tenant panel.

Each event **freezes what Phase 5 needs at the moment it happens** (plan 15.3): the link as the public API shows it, and a minimal payment (our IDs, status, amount as a decimal string and in minor units, currency, the late-payment flag, the decline count and a generic failure code). `payment.failed` carries the amount and currency too. The failure code is generic (card declined, insufficient funds, expired card, incorrect card details, authentication failed, processing error): Stripe's raw decline code can reveal fraud signals (a lost or stolen card) and stays on the attempt, in the tenant panel only. Later changes to the link or the payment never alter an event already recorded.

### 8. Reconciliation (plan 12.5, ADR-0050)

Every 15 minutes, per tenant and mode with open attempts or links in `processing`: payments under way at Stripe (3D Secure, authorized, processing) unchanged for 10 minutes are re-read from Stripe and applied through the same actions as the events. Attempts still waiting for a card are not visited: they cost nothing while they wait and close with their link. Each run visits the least recently visited payments first, at most 200 (configurable) and for at most 25 seconds; a visit counts even when Stripe fails, so a group of failing payments rotates to the back and can never starve a new one. A 3D Secure step left unanswered for 30 minutes (configurable) is canceled at Stripe as abandoned, which frees the link (or expires it); an authorization past the capture window is voided (authorize and capture happen seconds apart, so it means the flow stopped); a link stuck in `processing` with no payment under way is made payable again, or expired. An attempt closed without Stripe because its connection lost its credentials (a disconnected `api_key`) is flagged **needs review**, audited and shown on the attempt in the tenant panel: if a confirmation's answer was ever lost, a hold may remain on the payer's card until the bank releases it, and the merchant should check in Stripe. Closing a tenant's links is retried for up to two days (bounded by time, not by a count of tries), since links with a payment under way are waited for.

A closed attempt whose payment Stripe later reports as succeeded (for example a void that lost a race with a capture) is not reopened: it is flagged **needs review**, audited once and logged at critical level, since money may be unaccounted for.

**Job time limits.** A job still running when the queue hands it to another worker (`retry_after`, now 150 seconds) could run twice. Every queued job has its own limit below that (the payment and gateway-event jobs 115 seconds: two bounded Stripe calls plus the merchant's validation), and the workers' default limit is 120 seconds; a test keeps every job below `retry_after`. The deployment guides raise the workers' stop grace period accordingly.

The daily comparison of the last 48 hours of plan 12.5 is left for later (it needs listing payments per connection, which is a gate item).

### 9. Payer data (plan 19)

The Phase 4 page collects the whole MVP catalog as configured on the link: e-mail, full name, phone (country code list with Mexico first; stored in E.164), company, billing address (country, street, city, state, postal code; Mexican postal codes have 5 digits), tax ID and notes. The data is stored encrypted, apart from the financial rows, with its mode (test or live), a purge date of 24 months (the purge job is Phase 8), and never logged.
- **Privacy notice required** (plan 11.3, 19.2): a tenant without a privacy notice URL collects **no** payer data. The page hides every payer field (the payment itself still works), the omission is logged, and the tenant panel warns on each affected link. Refusing to create such links was rejected: the platform default asks for an optional e-mail, so every tenant without a URL would be blocked. When the merchant collects data, the page says the merchant receives it and links the merchant's privacy notice. Deviation from plan 19.1: phone numbers are checked by structure (length, the Mexican 10-digit rule) instead of libphonenumber, and the optional MX-record check of e-mail domains is not done.

### 9b. Client IP and user agent of attempts

The attempt and each decline keep the payer's full IP address and user agent. They are needed for card-testing investigations: the tenant and the platform must be able to see that many declines came from one address or network, and to match them with Stripe Radar and the web server's records. They are hidden from every serialization, never shown to other tenants, never sent to Stripe by us and never logged. Retention (plan 7.5 "limited retention", 19.2): Phase 8's purge clears them 90 days after the attempt closes, together with the payer-data purge; the financial record stays. Hashing or truncating them now was rejected: a hash cannot be matched with Radar or a provider's abuse report, and a truncated address cannot tell two customers of one network apart.

### 10. Security headers (plan 11.8, 23.4)

- A **nonce-based CSP** on every checkout response. Scripts and frames: the page itself, `js.stripe.com`, `*.js.stripe.com`, `hooks.stripe.com` (frames, 3D Secure) and `challenges.cloudflare.com`; requests: the page and `api.stripe.com`; styles and fonts: the page (styles with the nonce); images: the page and inline data; no framing of the page (`frame-ancestors 'none'`), no plugins, no base changes, forms only to the page. The same nonce is given to the asset and font tags. Google Maps (Stripe's address element) is not used.
- The headers wrap every response of the pay host, including session and CSRF errors (419) and any unknown path, which answers the same 404 page as an unknown token.
- `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (the token is in the URL), `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow` (and the robots meta), HSTS for two years with preload, `nosniff`.
- The web server keeps its own defaults for the other surfaces but no longer duplicates or contradicts what the application already sent; it serves the self-hosted font files with CORS so Stripe's card iframe can use Mukta.

### 11. The checkout sandbox

- On only when `AXISPAY_CHECKOUT_SANDBOX=true` **and** the environment is `local` or `testing`. **The application refuses to boot** when the flag is set in any other environment, and the sandbox gateway refuses live-mode links and connections.
- Server: a fake gateway keeps payments in the cache and follows the scenario the browser stub encodes in its confirmation token: approved, declined, insufficient funds, bank verification (3D Secure) and slow processing. Captures succeed, voids cancel, idempotency keys behave like Stripe's.
- Browser: the stub replaces Stripe.js (the real one is not loaded), shows a scenario picker in place of the card form and a "sandbox bank" dialog for 3D Secure, whose answer is posted to a route that only exists while the sandbox is on.
- `axispay:checkout:demo` (sandbox only) creates a demo tenant, a sandbox connection and links in every state, and prints their URLs.

### 12. Tenant panel

The link detail shows its payment attempts, read-only, to users with `payments:read`: status, amount, card brand and last four, card country, declines with the last decline code, whether it was paid late, the Stripe payment ID (support only), and dates. A blocked link shows the block and the unblock action. A separate payments list is left to Phase 7, together with refunds.

### 13. Public API

`payment_link.payment` stays `null` in Phase 4 and `GET /v1/payments` is not added: the plan places neither in Phase 4, and the `payment` object needs FX, payer and pre-validation blocks that later phases fill. The OpenAPI contract does not change.

### 14. Additions to the gateway port (plan 12.1)

`confirmPayment` takes the return URL; `capturePayment` is new (manual capture); `cancelPayment` takes an idempotency key (rule 5); the payment status is a provider-neutral enum with the authorized stage; a payment carries the client secret only while the browser must act, the card preview, the last payment error with a reference that identifies the decline, our attempt ID read back from the metadata and the authorization's expiry. The payment event kind is one (`payment updated`) because the handler always re-reads.

## Consequences

- Payers can pay links with cards, including 3D Secure, with the authorize-validate-capture flow; tenants see attempts and declines in the panel; the platform's database follows Stripe through events and reconciliation.
- Local development and the browser tests run the full flow in the sandbox; production can never enable it.
- Phase 5 plugs the merchant callback into the extension point and turns the recorded business events into webhooks; Phase 6 plugs conversion into the amount decision; Phase 8 adds the payer-data purge and branding; Phase 9 the superadmin alerts.
- Deployment: run the migrations, `axispay:stripe-sync-webhook-endpoints`, add the six events to both Connect destinations, set `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`, and make sure `AXISPAY_CHECKOUT_SANDBOX` is unset.
