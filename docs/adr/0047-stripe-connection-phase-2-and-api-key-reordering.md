# ADR-0047: Stripe connection in Phase 2 — MX platform, Standard-equivalent accounts, api_key brought forward

- **Status:** Accepted (owner decisions of 2026-09-26); the points marked *unverified* below wait for the Stripe contract tests with real test-mode keys
- **Date:** 2026-09-26
- **Source:** project owner decisions (2026-09-26); master plan sections 3 (ADR-004, ADR-005, ADR-017, ADR-019), 7.4, 7.6, 12, 14, 17.3, 21.3, 23.2, 26.2 (cases 3, 18–21), 27 (Phase 2 and Phase 4B); [ADR-0031](0031-tenancy-enforcement.md)

## Context

Phase 2 (plan 27) delivers the gateway port, `gateway_connections`, the credentials encrypter, the `platform_onboarding` flow (2A) and the Stripe Connect webhooks. The plan left `api_key` (2C) and `oauth` (2B) for Phase 4B and several Stripe details "to verify before implementing" (plan 12.3.4, section 29). On 2026-09-26 the project owner decided:

1. The platform Stripe account is in **Mexico (MX)**. Connected accounts are **MX by default, configurable**.
2. Connected accounts use **Standard-equivalent** controller properties (the merchant pays Stripe's fees and bears losses, Stripe collects the requirements, full Stripe Dashboard), set in configuration.
3. **`api_key` (2C) is brought forward into Phase 2**: the platform team is the first "tenant" and connects its own Stripe account with a restricted key (`rk_test_` / `rk_live_`) and a publishable key (`pk_`). `platform_onboarding` stays the recommended option in the panel; `oauth` stays disabled (configuration flag) until Phase 4B. A tenant must be able to move later from `api_key` to `platform_onboarding` (disconnect, then connect again: one active connection per provider and mode, ADR-004).

## Decision

### 1. Platform and connected-account configuration

- `config/services.php` → `stripe`: keys and webhook secrets per mode (`STRIPE_TEST_*`, `STRIPE_LIVE_*`), never mixed; a key of the wrong mode is refused by `PlatformStripeKeys`.
- **API version pinned** to `2026-08-26.dahlia` (`services.stripe.api_version`), the version of the installed SDK (`stripe/stripe-php` **v21.3.2**, latest stable on 2026-09-26). Every client (`StripeClientFactory`) and every webhook endpoint we create uses it. Changing it is a deliberate, staged change together with the fixtures in `tests/Fixtures/Stripe/<version>/`.
- `config/axispay.php` → `gateways.stripe`:
  - `allowed_countries` from `AXISPAY_STRIPE_ALLOWED_COUNTRIES` (default `MX`; the first entry is the default country of new accounts). Checked when creating a `platform_onboarding` account (the chosen country is sent as `country`, which Stripe then locks) and on `api_key` (the `country` of `GET /v1/account`).
  - `account_controller`: `fees.payer=account`, `losses.payments=stripe`, `requirement_collection=stripe`, `stripe_dashboard.type=full`. **Verified** as the documented Standard mapping, and a valid combination (`full` is only incompatible with `application` for losses, fees or requirement collection); Stripe's response shows `type: "standard"`. Source: [Migrate to controller properties](https://docs.stripe.com/connect/migrate-to-controller-properties), [Create an account](https://docs.stripe.com/api/accounts/create).
  - `connection_methods`: `platform_onboarding` and `api_key` enabled by default (env flags), `oauth` hard-coded `false`.
- **Accounts API v1** (`POST /v1/accounts`) is used. Stripe positions Accounts v2 as the richer API and describes v1 as "limited support", but v1 is documented and supported, and it is required for OAuth (Phase 4B). Revisit when Phase 4B or Stripe's deprecation notices make v2 necessary. Source: [Accounts v2](https://docs.stripe.com/connect/accounts-v2).
- *Unverified:* an explicit statement that an MX platform may create MX full-dashboard accounts (the domestic case; very likely). Cross-border payouts are not self-serve for MX platforms ([cross-border payouts](https://docs.stripe.com/connect/cross-border-payouts)), which is one reason other countries stay off by default. The contract test `creates a Standard-equivalent MX account` confirms it with the platform's test key.

### 2. platform_onboarding (2A)

- The connection row is created first; the account's idempotency key is `axispay-account-<connection id>`, so a retry after a partial failure returns the same Stripe account (rules.md rule 5). Stripe calls run outside transactions and row locks.
- Account Links: `type=account_onboarding`, `collection_options.fields=eventually_due`, return and refresh URLs on the app host (`/gateways/stripe/onboarding/{connection}/return|refresh`, controllers that only call actions). Links are single-use and expire after a few minutes ([Account Links](https://docs.stripe.com/api/account_links/create), [hosted onboarding](https://docs.stripe.com/connect/hosted-onboarding)). A new link needs `gateway:manage` and the re-authentication window: whoever opens it can enter the account's bank details. The refresh URL sends the user back to the page when the window is closed.
- The return does not mean onboarding is complete: the account is re-read (`SyncGatewayConnection`). Status rule: charges enabled → `active`; otherwise `restricted` once the connection could charge before, else `onboarding`.
- **Disconnecting is local.** Stripe does not let a platform deauthorize (`no_deauth_on_controlled_account`), reject (only when the platform is liable for losses) or delete (live full-dashboard accounts where Stripe covers losses) an account it created with these controller properties. The connection becomes `disconnected`; the merchant keeps their Stripe account. Sources: [OAuth reference](https://docs.stripe.com/connect/oauth-reference), [reject](https://docs.stripe.com/api/account/reject), [delete](https://docs.stripe.com/api/accounts/delete).

### 3. api_key (2C), brought forward

Validation order (plan 12.3.3; the first failure stops everything and nothing is stored; the refusal is audited with its reason only):

1. **Format:** a restricted key `rk_(test|live)_…`; any `sk_` is refused with an explanation, and so is anything that is not an `rk_`.
2. **Modes:** `rk_` and `pk_` share a mode, and it is the panel's current mode.
3. **Account:** `GET /v1/account` with the rk → account ID, country (allowed list), charges enabled. 401 → key rejected; 403 → the key cannot read the account.
4. **pk ↔ rk same account:** a single-use **PII token** is created with the pk (`POST /v1/tokens`, `pii[id_number]=000000000`, a dummy value) and read with the rk (`GET /v1/tokens/{id}`). 404 → the pk belongs to another account; 403 → the rk lacks `token_read`. Stripe documents that tokens can be created with a publishable key and that `GET /v1/tokens/:id` exists ([Tokens](https://docs.stripe.com/api/tokens), [PII tokens](https://docs.stripe.com/api/tokens/create_pii)); that a pk can't read account data ([API keys](https://docs.stripe.com/keys)). *Unverified:* that a token of another account answers 404 to the rk, and that the check behaves the same in live mode. It is the only server-side mechanism found; the browser fallback of plan 12.3.3 (Stripe.js with the pk) is kept as the alternative if the contract tests disprove it. Mitigation meanwhile: the account ID and mode are also checked through the rk, and a pk of another account would only break the checkout of this tenant (payments would fail to confirm), never move money elsewhere.
5. **Required permissions**, probed without side effects. Names from Stripe's permission reference ([Stripe Apps permissions](https://docs.stripe.com/stripe-apps/reference/permissions), [restricted keys](https://docs.stripe.com/keys/restricted-api-keys)); the Dashboard labels are assumed to match (*unverified*):

   | Permission | Why | Probe |
   |---|---|---|
   | `connected_account_read` (Accounts, read) | Country, charges enabled (FX rule, health check) | step 3 (*which permission governs `GET /v1/account` for an rk is unverified*) |
   | `token_read` (Tokens, read) | pk ↔ rk check | step 4 |
   | `payment_intent_write` (PaymentIntents, write) | Phase 4 charges | empty `POST /v1/payment_intents` |
   | `charge_write` ("Charges and Refunds", write) | Phase 7 refunds (Stripe bundles refunds with charges) | empty `POST /v1/refunds` |
   | `charge_read` | Reconciliation | `GET /v1/charges?limit=1` |
   | `dispute_read` | Disputes | `GET /v1/disputes?limit=1` |
   | `event_read` | Reconciliation | `GET /v1/events?limit=1` |
   | `payment_method_read` | Card country (FX) | `GET /v1/payment_methods?limit=1` (`customer` is optional now) |
   | `confirmation_token_read` | Deferred-intent checkout | `GET /v1/confirmation_tokens/<non-existent>` (404 = allowed) |
   | `webhook_write` (Webhook Endpoints, write) | The remote endpoint | creating it (a 403 there is reported as this missing permission) |

   Write probes send an **empty body** with an idempotency key: Stripe must answer 400 (missing parameters) when the key may write and 403 when it may not; an empty body can never create anything. Stripe does not document that permission is checked before parameter validation (*unverified*); the contract test `answers a permission probe with 403 or 400` confirms it.
6. **Excessive permissions:** `payout_write`, `transfer_write` (empty POSTs) and `balance_read` (`GET /v1/balance`). In test mode a warning and an e-mail; in **live mode an extra confirmation** is required (form checkbox), then the warning and the e-mail.
7. **Uniqueness:** the SHA-256 fingerprint of the rk may not be stored twice; the account may not belong to another tenant (any of its rows, disconnected ones included).

Then: the rk is encrypted with `GatewayCredentialsEncrypter`, the webhook endpoint is created on the merchant account (`POST /v1/webhook_endpoints` with the rk and the pinned `api_version`), and its secret (returned only on creation) is stored encrypted. Updating keys requires the same account and re-creates the endpoint (the old one is deleted best effort). Disconnecting deletes the endpoint while the key still works and overwrites every credential with NULL.

- **Direct events: only what the phase handles** (security review, 2026-09-26). A merchant account also carries sales the platform never made; subscribing to them would store their payer data. Phase 2 subscribes the direct endpoints to `account.updated` only (`axispay.gateways.stripe.direct_webhook_events`). Plan 14.3's full list (`payment_intent.*` names, `charge.refunded`, `refund.*`, `charge.dispute.*`; exact names, since partial wildcards are not documented — all verified in the [enabled_events enum](https://docs.stripe.com/api/webhook_endpoints/create)) is added by the phase that handles them, then `axispay:stripe-sync-webhook-endpoints` updates every existing endpoint (`POST /v1/webhook_endpoints/{id}` with the new `enabled_events`, idempotency key per run and connection) without reconnecting. Stripe's update does not take `api_version`: a new pinned version needs the endpoints re-created ("Update keys").
- **Nothing half-created is kept** (security review): any failure after the row is stored (endpoint creation, activation) deletes the remote endpoint if it exists and the row, then rethrows. When a key update fails after its new endpoint was created (including losing a fingerprint-uniqueness race to another tenant, which is answered as "key already linked" instead of a 500), the new endpoint is deleted and the connection keeps its old key and endpoint.
- **Idempotency keys per operation:** every create call of a connect or key update derives its key from one ULID generated for that attempt (stable across the SDK's automatic retries). Submitting the same key again later is a new operation and never replays an earlier response.
- **Stale-credential guard:** a failing call records the fingerprint of the key it used; `invalid_credentials` is only set under the row lock if the stored fingerprint still matches. A revoked OLD key cannot block keys rotated while the call was in flight.

- 401 and 403 are both treated as access problems whatever the error `type`: Stripe documents a missing restricted-key permission both as a 403 permission error and as an "invalid request error" ([errors](https://docs.stripe.com/api/errors), [restricted keys](https://docs.stripe.com/keys/restricted-api-keys)). A revoked key answers 401.
- Health check: `axispay:gateways:check-api-keys` (daily at 06:00, `withoutOverlapping()->onOneServer()`) queues one `CheckApiKeyConnectionsJob` per connection (TenantAware, payload = connection ID only). An authentication or permission error → `invalid_credentials` (e-mail once, audited); an outage only records the check; a success syncs the account and heals `invalid_credentials`.
- **The rk never leaves memory in clear (plan 26.2 case 19):** `ApiKeyCredentials` refuses serialization and hides the value from dumps; `#[SensitiveParameter]` on every parameter that carries it; the Stripe SDK exception (whose trace holds the key as an argument) is never kept as `previous`, only its code, request ID and status; only `rk_live_…last4` is ever shown; jobs carry the connection ID. A test drives the success and failure paths and inspects the written logs, audit rows, exceptions, job payloads and panel responses.
- **The panel keeps the typed rk for one request only** (security review): Filament validates an action form before the action callback, and a validation error returns the component snapshot with the form data. The Stripe page therefore erases the key from every mounted action in its Livewire `rendering()` and `dehydrate()` hooks, which run on every response (success, domain refusal, form validation error). A refused form comes back with the key field empty. Browser submissions send the deferred field together with the submit call, so the key only exists server-side during that request. Tests submit the form like a browser (one request) and assert the key is absent from the HTML, snapshot, effects, errors and logs for every validation failure.
- The panel secret field is `PasswordField::forSecret()` (ADR-0046's component, own reveal labels, no autocomplete, password managers told to ignore it).

### 4. Incoming webhooks and routing

- `POST /webhooks/stripe/connect/{test|live}` and `POST /webhooks/stripe/direct/{connection_id}` on the API host, outside `/v1` (not public API; no OpenAPI entry), `api` middleware only (no session, no CSRF), `throttle:1200,1`, API error format.
- The URL mode only selects the signing secret: **the event is routed by its own `livemode` and `account`**, because Stripe also delivers test events of connected accounts to live Connect endpoints ([Connect webhooks](https://docs.stripe.com/connect/webhooks)). Signature verification: `\Stripe\Webhook::constructEvent` on the raw body, default tolerance 300 s ([webhooks](https://docs.stripe.com/webhooks)).
- **Stored payload** (plan 14.4, security review): an event of a kind the platform does not handle is stored directly as `ignored`, without a job, and with a **reduced payload** (id, type, account, mode, created, API version, object ID and type; `axispay_reduced: true`), never the object's data. Unroutable events keep the reduced payload too. `axispay:provider-events:purge` (daily 03:30, `withoutOverlapping()->onOneServer()`) deletes `ignored` and `unroutable` rows older than 7 days and reduces the payload of `processed`/`failed` rows older than 30 days (`axispay.gateways.stripe.provider_events`). The reduction lives in the adapter (`PaymentGateway::reduceWebhookPayload()`, another addition to the port). The purge runs across tenants through `ProviderEvents\Services\ProviderEventRetention` (scope-bypass whitelist).
- **Routing happens when the event is stored** (not in the job): the row is written in its tenant from the start, so `tenant_id` never changes after insert (BelongsToTenant keeps it immutable). An event whose account matches no connection is stored as `unroutable` (platform row, `tenant_id` NULL) and logged at alert level; the superadmin e-mail for platform alerts arrives in Phase 9 (plan 22). Known limitation: an `account.updated` racing the few milliseconds between Stripe creating an account and our row storing its ID is stored as unroutable; the return URL and the next event re-sync the connection.
- Direct endpoint: unknown, non-api_key or disconnected connection → 404; the event must belong to the connection's account and mode. Plan 14.2 asks to delete the remote endpoint of a disconnected connection in the background: impossible, because disconnecting already destroyed the key; the endpoint is deleted at disconnection instead (best effort).
- `ProcessProviderEventJob` (`critical` queue, 5 tries with backoff, TenantAware) only processes `received` rows (idempotent, plan 26.2 case 3), re-reads the object from Stripe (ADR-017) and applies it through the Gateways actions: `account.updated` → `SyncGatewayConnection`; `account.application.deauthorized` (Connect only) → disconnect **only if Stripe now denies access** (a stale or replayed event is ignored); every other type → `ignored` until Phases 4 and 7.

### 5. Other decisions

- **Port deviations (ADR-019, plan 12.1):** `parseWebhook()` takes a third argument, `WebhookSource` (Connect endpoint of a mode, or one connection), because the signing secret depends on the endpoint; `reduceWebhookPayload()` (above) and `eventKind()` were added so the event pipeline never matches Stripe type strings itself. The payment and refund methods keep the plan's signatures and throw `GatewayOperationNotImplementedException` until Phases 4 and 7. `FakePaymentGateway` (tests) implements the whole port.
- **Uniqueness of the account:** the database unique `(provider, provider_account_id, livemode)` applies to non-disconnected rows only (generated `active_provider_account_id`), so a tenant can reconnect the same account after disconnecting (key rotation by disconnect/connect, or back to an account). The application refuses an account that any row of another tenant ever held. `credentials_fingerprint` is unique while stored (credentials are NULL after disconnecting). An extra column `details_submitted` is kept from the Account object.
- **Tenant activation (plan 21.3):** the first connection that can charge, in **either mode**, moves the tenant from `pending_onboarding` to `active` through `ChangeTenantStatus::handleAsSystem()` (same transition rules, row lock, audited with the system actor; closing is never automatic). Test-mode integration must not wait for live onboarding, and creating links in a mode still requires a connection that can charge in that mode (`gateway_not_ready`, Phase 3).
- **Credentials key:** `GATEWAY_CREDENTIALS_KEY` (`base64:` + 32 random bytes, AES-256-GCM), refused when missing, malformed or equal to `APP_KEY`; `GATEWAY_CREDENTIALS_KEY_VERSION` tags each ciphertext; `GATEWAY_CREDENTIALS_PREVIOUS_KEYS` keeps old versions readable while `axispay:rotate-gateway-credentials-key` re-encrypts. The webhook signing secret of a direct endpoint uses the same key and version.
- **DELETE calls** (removing a webhook endpoint) carry no idempotency key: Stripe ignores keys on DELETE, which is idempotent by nature.
- **Whitelist (ADR-0031):** `Gateways\Services\GatewayConnectionResolver` was already on the plan's list; it now exists and holds every cross-tenant lookup (webhook routing, uniqueness, health-check scheduling, key rotation, endpoint sync, the platform panel's read-only view). `ProviderEvents\Services\ProviderEventRetention` is added for the retention purge; everything else on `provider_events` is written in its tenant context or as explicit platform rows.

## Consequences

- The platform team can connect its own account with rk + pk in Phase 2; the step-by-step guide (keys to create, permissions to grant, webhook URLs) is in `docs/development.md`.
- Phase 4B keeps: OAuth (2B), end-to-end payments with the three methods, and the confirmation of the *unverified* points above through `./vendor/bin/pest --group=stripe` with real test-mode keys (`STRIPE_TEST_SECRET`, `STRIPE_CONTRACT_RESTRICTED_KEY`, `STRIPE_CONTRACT_PUBLISHABLE_KEY`, optionally `STRIPE_CONTRACT_OTHER_PUBLISHABLE_KEY`).
- Phase 3 adds the link side of plan 12.3.4 (cancel active links on disconnect, `gateway_not_ready` on link creation).
- The superadmin e-mail for unroutable events and failed events is Phase 9 (alerts); until then they are `alert`/`error` log lines.
