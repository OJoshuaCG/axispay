# ADR-0064: Link line items, a signed return to the merchant with an optional automatic redirect, and links that collect no payer data

- **Status:** Proposed. Requested by the integration with pbx-payments (2026-10-06), which sends its priced top-up (purchase, processing charge, VAT) to a hosted page and expects the payer back on its own site with a result it can trust. It needs the owner's acceptance.
- **Date:** 2026-10-09
- **Source:** the `cirox-payment-links` change (spec B6 hosted breakdown and B7 return redirect, tasks CRX-9, CRX-10 and CRX-11); [ADR-0048](0048-payment-links-api-phase-3.md), [ADR-0051](0051-checkout-and-card-payments-phase-4.md), [ADR-0056](0056-checkout-experience-legal-texts-merchant-logo-and-theme.md), [ADR-0058](0058-pre-payment-validation-phase-5.md), [ADR-0063](0063-currency-conversion-tenant-fixed-rate-and-payment-settings.md); plan sections 11.2, 11.3, 11.5, 11.8, 19.

## Context

A link had one `description` and one amount. pbx-payments prices a top-up as purchase + processing charge + VAT and wants the payer to see that breakdown on the hosted page, also when the card is converted to MXN (ADR-0063), where the lines must still add up to the amount charged to the cent. After paying, the payer stays on AxisPay: `return_url` only showed a button, appended nothing and the integrator was told not to trust the return. pbx needs the payer sent back by themselves, with something its return page can verify. Finally, pbx already knows who the payer is and wants links that ask for nothing but the card.

## Decision

1. **`line_items` on link creation.** An optional list of `{label, amount, absorbs_rounding}` in the link's currency. It is display only: the link keeps its single `amount`, which is what is charged. Rules (all refused with `parameter_invalid` or the amount codes, with the item's `param`, e.g. `line_items.1.amount`): a non-empty list of at most 20 items; label 1 to 100 characters after trimming; amount a decimal string greater than zero with the currency's decimals (the minimum and maximum charge of a whole payment do not apply to a part); `absorbs_rounding` an optional boolean, at most one line with `true`; **the amounts add up exactly to the link amount**; and, when the link can be converted to MXN (USD link, resolved `fx.mode` not `none`), **exactly one line has `absorbs_rounding: true`**. The lines are stored as JSON on the link (`line_items`, minor units) and returned in the link object as `line_items` (`null` when none).
2. **Hosted page.** The order summary lists the lines (escaped text, the link's currency) above the total, while the amount is shown (active and processing links, and the session that just paid, like the total). When the payer's card is converted, the currency confirmation shows the lines converted: each line is converted on its own (`FxConverter`, round half up once) and the line with `absorbs_rounding` takes the residual, so the converted lines add up to exactly the MXN amount of the quote (12.30 USD at 17.4225: 10.00 becomes 174.23, the flagged 2.30 becomes 40.07, total 214.30). If that cannot be done honestly (not exactly one flagged line, or a residual that is zero or negative because many tiny lines rounded up) the lines are left out of the confirmation and the total stands alone: the amount is never wrong, only the breakdown is omitted. Metadata and the client reference stay off the page, as before.
3. **`auto_redirect`.** An optional boolean of link creation, default `false`, only valid with a `return_url` (`parameter_invalid` on `auto_redirect` otherwise). Frozen on the link. The countdown length is a platform setting (`axispay.checkout.redirect_countdown_seconds`, 5 seconds), not a per-link value. The paid page shows "We will take you back to X in N s" with a "Stay here" button; the countdown is rendered hidden and only the page script shows it, so without JavaScript nothing promises a redirect and the "Return" button remains. Only the session that just paid is sent back by itself: a payer who reopens a paid link later sees "already paid" with the button, never an automatic redirect (it would loop with a merchant page that links back). The script only follows `http(s)` URLs, which the server wrote.
4. **Signed proof on every return after a payment.** The button and the redirect (and the `return_url` of the polled status) point to the merchant's `return_url` with these query parameters appended after its own, before any fragment: `ref` (the link's `client_reference_id`, left out when it has none), `plink` (`plink_...`), `payment` (the `pay_...` that paid it), `status=paid`, `ts` (Unix seconds when the page was built) and `sig`. `sig` is the lowercase hex HMAC-SHA256 of `plink\npayment\nstatus\nts\nref` (`ref` empty when absent; it is the only free-form field and goes last, so the message is unambiguous) keyed with the tenant's **return signing secret**; during a rotation `sig` holds one signature per active secret separated by a comma, and the merchant accepts the proof when any of them matches one of its secrets (the same overlap the webhook and validation headers use). Neither the checkout token nor any gateway identifier or secret is ever part of the URL. The merchant must also check `ts` is recent (it recommends 24 hours at most: the proof is built each time the paid page is rendered) and must not treat the proof as the authority on the payment: it confirms it with the API (`GET /v1/payments`) or a webhook. The proof only tells its page that the query string was written by AxisPay, not typed by the payer. A link paid before this change gets the same proof when its paid page is shown, and a paid link with no payment to prove (it cannot happen in production) gets the plain URL.
5. **Return signing secret.** One per tenant and mode (`return_signing_secrets`, encrypted `secret`, `previous_secret` and its expiry, `rsec_` + 64 hex characters), created the first time a proof is needed. It rotates without downtime like the validation secret: the previous one keeps signing 24 hours (`axispay.checkout.return_previous_secret_hours`), rotating again inside the window drops the oldest. A "Return secret" action on the Payment settings page (`settings:manage`, re-authentication, writable panel) rotates it and shows the new secret once; the first rotation is how a merchant reads it. Audited as `return_secret.rotated`, never with the secret.
6. **Return action on closed links.** The expired and canceled pages show the same "Return to X" button with the merchant's plain `return_url`: nothing is proven, because nothing was paid. A link blocked for card-testing (`unavailable`) does not offer it.
7. **CSP.** No change: the redirect is a script navigation, which Content-Security-Policy does not restrict (`form-action` only covers forms), the redirect script is part of the existing nonce-protected module, and the merchant's domain was already validated against `allowed_return_domains` at creation.
8. **Payer fields all `hidden`.** Confirmed, no code change: the page renders no payer field, a payment completes with no payer data, nothing is stored in `payer_details`, the validation body's `data.payer` is `null`, and payer values sent anyway for a hidden field are ignored (the validator skips hidden fields). Covered by `HiddenPayerFieldsTest`. What stays is the card form itself: the Payment Element may still ask for a card's own country and postal code, which is card data, not payer data.

## Consequences

- pbx-payments can send the three-line breakdown, show it also in MXN, and verify the return with its secret and the payments API. Merchants that already used `return_url` now receive extra query parameters on the return (additive; their own parameters are kept). The integration guide documents how to verify the signature.
- A link that can be converted must flag its rounding line; existing links have no lines, so nothing changes for them.
- Rotation needs the merchant to read the secret once from the panel before verifying; a link created with `return_url` and paid before that works, the proof is signed with the generated secret, and the first rotation keeps it valid for 24 hours.
- The countdown length is not configurable per link: if a merchant needs it, `auto_redirect` can become an integer later without breaking `true`/`false`.
- Not covered: creating line items in the panel's link form (API only for now), showing them on the link's detail in the panel, and `payment.*` events carrying them (the merchant that sent them already has them).
