# ADR-0066: Refunds, voiding an authorization by API, and refund and dispute events (Phase 7 subset)

- **Status:** Proposed. Requested by the integration with pbx-payments (2026-10-06, milestone M6: "refund/dispute events consumer; retire the manual path"); it needs the owner's acceptance. Extends [ADR-0062](0062-payment-canceled-event-and-payments-read-api.md) (payment events and reads) and [ADR-0057](0057-outgoing-webhooks-delivery-phase-5.md) (event catalog); keeps [ADR-0012](0012-fees-on-refunds-and-disputes.md) (platform fees are not returned).
- **Date:** 2026-10-06
- **Source:** plan 10.7, 14.3, 15.2, 16; [ADR-0050](0050-linear-payment-flow-authorize-validate-capture.md), [ADR-0051](0051-checkout-and-card-payments-phase-4.md); the `cirox-payment-links` change (spec B10; tasks CRX-13 and CRX-14); owner decisions of 2026-10-06 (refunds within about a week of delivery; AxisPay only administers the payment: what a refund or a dispute means for the integrator's business is the integrator's decision).

## Context

The port had refund methods that threw "Phase 7", `refund.*` and `dispute.*` were in the event catalog but never sent, and `refund_status` and `dispute_status` of a link were always `none`. pbx-payments credits balances and records invoice payments from the events it receives, so it needs to refund through the API and to learn about refunds made elsewhere (Stripe's Dashboard) and about disputes, without anybody looking at Stripe.

## Decision

1. **`POST /v1/refunds`** (scope `refunds:create`, `Idempotency-Key` required) refunds a **captured** payment (`succeeded`), fully (no `amount`) or in part, in the **currency charged** (MXN after a conversion), with an optional `reason` (`requested_by_customer`, `duplicate`, `fraudulent`, `other`). `GET /v1/refunds` (filters `payment`, `status`; cursor pagination like the other lists) and `GET /v1/refunds/{id}` (scope `refunds:read`). The existing codes `refund_exceeds_available` (422) and `payment_not_refundable` (409) are now used. IDs are `re_<ULID>`; no gateway ID ever leaves.
2. **The reservation is made in the database before the gateway is asked.** In one transaction (link, then attempt, locked: rules.md rule 8) the amount must fit in `payment - (refunds pending + succeeded)`, so two simultaneous refunds can never add up to more than the payment, and a refund still `pending` holds its money. The row is stored `pending` with audit (`refund.requested`) and `refund.created`. Then, outside any transaction (rules.md rule 7b), the gateway is asked on the connection the payment was made with, under the key `axispay:refund:{refund_id}`; `ApplyProviderRefund` applies the answer.
3. **What the call answers.** `201` with the refund as the gateway reports it (card refunds mostly come back `succeeded`, some `pending`: the plan's "201 pending" is relaxed to the truth); the final state arrives as an event. A gateway that **refuses** (a request error) or whose credentials no longer work fails the refund at once (`failed`, `failure.code` `gateway_refused` or `gateway_access_denied`, `refund.failed`): the answer is still `201`, so a replay returns the same thing and the money is free again. A gateway that **cannot be reached** leaves the refund `pending` and answers `502 gateway_error` (never stored by the idempotency layer): the retry with the same key finishes the same refund, first looking for a refund the gateway made whose answer was lost (our refund ID travels in its metadata) so it is never made twice. Stripe keeps answering a stored 5xx under the same key, so one 5xx is repeated once under the derived key `:r1` after the same lookup. The refund row also keeps `idempotency_key` / `idempotency_request_hash` (unique per tenant and mode), like links.
4. **One action applies every refund state** (`ApplyProviderRefund`), like `ApplyProviderPayment`: the API call, the webhook handler and the reconciliation all come to it. It finds the refund by the gateway's ID or by our ID read back from the metadata; a refund that is neither is a refund made in the gateway's own dashboard and is **imported** (`origin: provider_dashboard`, `refund.created`). A refund of another payment or currency is never adopted. States move forward only (`pending` to `succeeded`, `failed` or `canceled`; a `succeeded` one can still `fail`; `failed` and `canceled` are final), so duplicate and out-of-order reports change nothing and announce nothing. `payment_attempts.amount_refunded_minor` is kept equal to the sum of the succeeded refunds and the link's `refund_status` follows (`none`, `partial`, `full`).
5. **Voiding by API.** `POST /v1/payments/{id}/void` releases an authorization that was not captured (`requires_capture`) with scope `refunds:create` (no new scope: undoing a charge is the same sensitive permission whether it was captured or not). It is `VoidAuthorization` with the new reason `merchant_requested`, so it takes the attempt's **lease** like the capture and the validation do: whoever holds it decides, the other backs off (`409 payment_busy`, retry in seconds). A capture that won the race (the payment is `succeeded`) or any other status answers `409 payment_not_voidable` (refund it instead); a payment already `canceled` answers `200` unchanged; an unreachable gateway answers `502` with nothing changed. `payment.canceled` carries `reason: merchant_requested`. The link goes back to `active` like after any release: closing it is the integrator's own business decision (cancel the link). The two new error codes are additions to the catalog.
6. **Incoming events.** `charge.refunded`, `refund.created|updated|failed` and `charge.dispute.created|updated|closed` become three provider-neutral kinds (`PaymentRefundsChanged`, `RefundUpdated`, `DisputeUpdated`). Their objects carry no metadata of ours, so `RecordProviderEvent` finds the attempt by the PaymentIntent in the payload among the tenant's attempts; none means `foreign_object` (ignored, reduced payload, before any gateway call, plan 14.4). `ProcessProviderEvent` re-reads from the gateway, never trusting the payload (ADR-017): one refund, every refund of the payment (this also covers refunds made in the Dashboard), or the dispute. Only the adapter knows Stripe's charges: the domain names the payment, and the adapter refunds the PaymentIntent. Both Stripe webhook destinations (Connect, and the merchants' own endpoints) subscribe to the seven event names; `axispay:stripe-sync-webhook-endpoints` updates the existing ones.
7. **Events to the integrator** (`DomainEventType` additions, recorded in the transaction that applies the change, so exactly once): `refund.created`, `refund.succeeded`, `refund.failed` (also for a refund the gateway canceled), `dispute.created`, `dispute.closed`. `data.object` is the refund or the dispute and `data.payment` the payment (with `client_reference_id`, `amount_refunded`, `refund_status`, `dispute_status`), frozen. The payment object of every payment event and of `GET /v1/payments` gains `amount_refunded`, `amount_refunded_minor`, `refund_status` and `dispute_status`. The refund's `failure` is a generic code (`refund_failed`, `refund_canceled`, `gateway_refused`, `gateway_access_denied`, `refund_not_sent`): the gateway's own reason stays internal.
8. **Disputes are recorded, not handled.** With direct charges the merchant answers them in the gateway's dashboard. A dispute row (`dsp_<ULID>`, `disputes` table) keeps the status (`needs_response`, `under_review`, `won`, `lost`, `warning_closed`), the reason as plain text, the evidence deadline and the dates; `dispute.created` is sent when it appears (also when it is first seen already closed, followed by `dispute.closed`) and `dispute.closed` when it closes. The link's `dispute_status` summarizes its payment's disputes: `open` while any is open, else `lost` if any was lost, else `won`; an inquiry that closed without a chargeback (`warning_closed`, or Stripe's `prevented`) counts as `won`, as no money was lost. There is no dispute endpoint.
9. **Reconciliation.** The 15-minute reconciliation (`axispay:payments:reconcile`) also covers refunds: a refund `pending` for 10 minutes is re-read (one refund, or every refund of the payment when it has no gateway ID, which finds one whose answer was lost); one that never reached the gateway and is a day old is failed (`refund_not_sent`), freeing its money, because the gateway's idempotency keys last 24 hours and nobody is going to retry it.
10. **Panel: read only.** The payment detail shows a "Refunds and disputes" section (amount refunded, summaries, the refunds with state, reason, origin and date, the disputes with state, reason and evidence deadline) when there is something to show. Creating a refund from the panel (permission `payments:refund` with re-authentication, plan 16.1) is **not** part of this change.
11. **Platform fees are not returned** (ADR-0012), and none is taken today (ADR-011); `refund_application_fee` is never sent.

## Consequences

- Two tables (`refunds`, `disputes`), both tenant tables (config/tenancy.php), and no new columns on `payment_attempts` or `payment_links` (they already had `amount_refunded_minor`, `refund_status` and `dispute_status`).
- The port gains `listRefunds` and `retrieveDispute`; `refund` and `retrieveRefund` are implemented; the "not implemented" exception is removed. The sandbox gateway refunds like the real one and has no disputes.
- Endpoints that subscribed to an explicit list of events do not receive the new ones until they add them; "every event" endpoints do. The additions to the payment object are compatible.
- A merchant connected with a restricted key already needs Charges and Refunds (write) and Disputes (read) since Phase 2; existing endpoints need `axispay:stripe-sync-webhook-endpoints` and both Connect destinations need the new events, or refunds made in the Dashboard and disputes only arrive through the reconciliation (refunds) or not at all (disputes).

## Alternatives considered

- **A `payments:void` scope.** Cleaner naming, but it adds a tenant permission, role changes, panel and key-form wording for the same sensitive power; reusing `refunds:create` keeps the catalog small. Revisit if an integrator needs refund and void separated.
- **Cancelling the link when voiding.** It is a business decision (the payer may be allowed to retry): the integrator cancels the link itself if it wants to.
- **Answering `201 pending` always.** Hides the gateway's real state; the event and `GET /v1/refunds/{id}` carry the final state either way.
- **Returning an error when the gateway refuses.** A replay of a stored 4xx would repeat the refusal for 24 hours and the integrator could not distinguish "never made" from "refused"; a stored `failed` refund is a single, auditable answer.
- **Treating `charge.refunded` as the only refund event.** It does not carry the refund's own state transitions; `refund.*` are handled too, and both lead to the same re-read.

## Unverified

Not run against the real Stripe (tests use Stripe's HTTP layer faked and fixtures of the pinned API version): the exact event names `refund.created`, `refund.updated`, `refund.failed` and `charge.dispute.*` on both destination types, that a refund of a card payment on a connected account comes back `succeeded` or `pending` as described, `refund_application_fee` being unnecessary for direct charges, and the dispute statuses (`warning_*`, `prevented`). Confirm them with the Stripe contract tests before the cutover soak (`CRX-0`).
